# Repository Instructions

## Repository orientation

- **Top-level overview and quick start:** [`README.md`](README.md)
- **VM / lab bootstrap (clone + Ubuntu `compute_init`):** [`init_cybr_demos.sh`](init_cybr_demos.sh)
- **Shared demo bootstrap:** `demos/setup_env.sh` (requires `CYBR_DEMOS_PATH` and `demos/tenant_vars.sh`)
- **Optional disposable lab tooling:** [`CYBR_LAB_TOOLING.md`](CYBR_LAB_TOOLING.md)

## Demo Documentation

When creating or updating demo documentation under `demos/`, follow the guidance in:

- `demos/guidelines/demo_md_guidelines.md`

Key expectation:

- Use `demo_setup.md` for setup and deployment documentation.
- Use `demo_validation.md` for post-install validation walkthroughs.
- Assume the demo is already installed.
- Focus on post-install validation.
- Explain both platform behavior and CyberArk behavior.
- Organize walkthroughs around the major integration patterns in the demo.
- Include at least one Mermaid flow diagram in every `demo_validation.md` that shows the runtime request path.

## Lab Tooling

`CYBR_LAB_TOOLING.md` documents an optional way to create disposable lab infrastructure for demo setup, validation, or end-to-end testing. Use it when a fresh lab is needed and suitable infrastructure is not already available.

Key expectations:

- Treat `cybr-lab-*` as an optional infrastructure creation path, not a required path for every demo.
- Use the shared `cybr-lab-*` commands from the `spin_cfn` tooling instead of copying lab spin scripts into this repo when this optional path is appropriate.
- Keep real lab configuration in `~/.cybr-labs/config.env`, not in this repo.
- Keep generated lab artifacts under `~/.cybr-labs/artifacts/`, not under `cybr-demos`.
- Do not commit one-off lab IDs, EC2 hostnames, public IPs, SSH key paths, workflow branch names, or environment names.
- When documenting validation, describe the reusable command flow and refer to `cybr-lab-output` for current connection details.

## Git Commit Hygiene

Before preparing a commit, review exactly what is staged and remove anything that is lab-local, generated, or sensitive.

Minimum checks:

- Run `git status --short` and confirm the staged file list matches the intended change.
- Run `git diff --cached --stat` and `git diff --cached --check`.
- Review `git diff --cached --name-only` for generated output, caches, machine-local files, and unrelated edits.
- Check staged shell scripts for executable mode with `git diff --cached --name-only --diff-filter=ACM | awk '/\.sh$/ {print}' | while read -r f; do git ls-files -s -- "$f"; done` and confirm each `.sh` file uses mode `100755`.
- Search the staged diff for credentials, tokens, private keys, local paths, personal identifiers, and temporary lab hosts.
- Check ignored and untracked files near the changed area with `git ls-files --others --exclude-standard <path>` and `git status --ignored --short -- <path>`.

Do not commit:

- Real tenant values from `demos/tenant_vars.sh` or shell environment exports.
- Cloud access keys, CyberArk service account secrets, Conjur tokens, API tokens, private keys, kubeconfigs, or certificates.
- Machine-local paths such as `/Users/...`, Google Drive sync paths, home-directory paths, or IDE metadata.
- Temporary lab instance identifiers such as specific EC2 hostnames, public IPs, or one-off validation targets.
- Terraform state, `.terraform/`, provider plugin caches, or other generated install artifacts.
- Code or documentation attribution lines such as `Authored by`, `Generated by`, `Created by`, `Co-authored-by`, or AI/tool signatures unless the user explicitly requests them.

Allowed when intentional and documented:

- Demo placeholder values such as `ChangeMe`, `Cyberark1`, or fake API keys that are clearly not tenant credentials.
- Small vendored demo assets required for offline or lab setup, such as Helm chart archives, when their source is documented.
- Terraform configuration files. `.terraform.lock.hcl` should follow the repo ignore policy unless the demo explicitly requires committing it for reproducibility.

If a commit includes intentionally staged demo secrets or binary artifacts, call them out in the final commit review so the reviewer can distinguish deliberate demo material from accidental leakage.
